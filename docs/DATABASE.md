# Database Design — TaskFlow

**Project:** TaskFlow — Smart Task & Workflow Management Platform
**Database:** MongoDB (document store)
**Document version:** 1.1
**Last updated:** 2026-06-23

This document defines the MongoDB data model: collections, fields, relationships, indexing, validation, and example documents. The model is intentionally lean and denormalised where it helps read performance, while keeping ownership and referential intent explicit.

---

## 1. Data Model Overview

TaskFlow has three primary collections:

| Collection | Purpose |
|------------|---------|
| `users` | Account records and profile data. |
| `categories` | User-defined, colour-coded groupings of tasks. |
| `tasks` | The core work items, each owned by a user and optionally assigned to one category. |

### 1.1 Relationships

```
            ┌──────────────┐
            │    users     │
            │  _id (PK)    │
            └──────┬───────┘
       1            │            1
       │            │            │
       │ owns       │ owns       │
       ▼            ▼            
┌──────────────┐   ┌──────────────────────────┐
│  categories  │   │          tasks           │
│  _id (PK)    │   │  _id (PK)                │
│  userId (FK) │◀──│  userId   (FK → users)   │
└──────────────┘ 0 │  categoryId (FK,nullable │
              └─── │             → categories)│
            many   └──────────────────────────┘
```

- **users → tasks:** one-to-many. A user owns many tasks; each task references exactly one `userId`.
- **users → categories:** one-to-many. A user owns many categories.
- **categories → tasks:** one-to-many, optional. A task may reference zero or one `categoryId`. Categories are scoped to the same owning user as the task.

> MongoDB has no foreign-key enforcement. Referential integrity (a task's `categoryId` and `userId` belong together, and the category exists and is owned by the user) is enforced in the application service layer.

## 2. Collection: `users`

### 2.1 Fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `_id` | ObjectId | yes | Primary key, generated by MongoDB. |
| `name` | String | yes | Display name. 2–60 chars. |
| `email` | String | yes | Login identifier. Lowercased, unique. |
| `passwordHash` | String | yes | BCrypt hash. Never returned by the API. |
| `role` | String (enum) | yes | `USER` or `ADMIN`. Defaults to `USER`. |
| `avatarUrl` | String | no | Optional profile image URL. |
| `timezone` | String | no | IANA timezone (e.g. `Asia/Kolkata`). Defaults to `Asia/Kolkata` (set on the `User` document at registration). |
| `createdAt` | Date | yes | Set on insert. |
| `updatedAt` | Date | yes | Set on every update. |

### 2.2 Indexes

| Index | Type | Reason |
|-------|------|--------|
| `{ email: 1 }` | unique | Enforce one account per email; fast login lookup. |
| `{ role: 1 }` | standard | Admin/aggregate queries by role. |

### 2.3 Validation rules

- `email` must match a standard email pattern and be unique (case-insensitive — stored lowercased).
- `name` length 2–60.
- `role` must be one of `["USER","ADMIN"]`.
- `passwordHash` is required and non-empty (set only by the backend).

## 3. Collection: `categories`

### 3.1 Fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `_id` | ObjectId | yes | Primary key. |
| `userId` | ObjectId | yes | Owner. References `users._id`. |
| `name` | String | yes | Category label. 1–40 chars. Unique per user. |
| `color` | String | yes | Hex colour (e.g. `#54C8EE`). Used in the UI. |
| `createdAt` | Date | yes | Set on insert. |
| `updatedAt` | Date | yes | Set on every update. |

### 3.2 Indexes

| Index | Type | Reason |
|-------|------|--------|
| `{ userId: 1, name: 1 }` | unique compound | A user can't have two categories with the same name; fast per-user listing. |
| `{ userId: 1 }` | standard | List all categories for a user. |

### 3.3 Validation rules

- `name` length 1–40; unique within a given `userId`.
- `color` must match a 6-digit hex colour pattern `^#([0-9A-Fa-f]{6})$`.
- `userId` is required and set by the backend from the authenticated principal.

## 4. Collection: `tasks`

### 4.1 Fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `_id` | ObjectId | yes | Primary key. |
| `userId` | ObjectId | yes | Owner. References `users._id`. |
| `categoryId` | ObjectId | no | Optional. References `categories._id` (same owner). |
| `title` | String | yes | Short task title. 1–120 chars. |
| `description` | String | no | Longer details. 0–2000 chars. |
| `status` | String (enum) | yes | `TODO`, `IN_PROGRESS`, or `DONE`. Defaults to `TODO`. |
| `priority` | String (enum) | yes | `LOW`, `MEDIUM`, or `HIGH`. Defaults to `MEDIUM`. |
| `dueDate` | Date | no | Optional deadline. |
| `completedAt` | Date | no | Set when status becomes `DONE`; cleared otherwise. |
| `tags` | String[] | no | Optional free-text tags (future-friendly). |
| `position` | Number | no | Ordering hint within a status column (for board view). |
| `createdAt` | Date | yes | Set on insert. |
| `updatedAt` | Date | yes | Set on every update. |

### 4.2 Indexes

| Index | Type | Reason |
|-------|------|--------|
| `{ userId: 1, status: 1 }` | compound | The most common query: a user's tasks filtered by status. |
| `{ userId: 1, dueDate: 1 }` | compound | Sorting/filtering by deadline; overdue detection. |
| `{ userId: 1, priority: 1 }` | compound | Filtering by priority. |
| `{ userId: 1, categoryId: 1 }` | compound | Tasks within a category. |
| `{ title: "text", description: "text" }` | text | Keyword search across title and description. |

> **Indexing strategy.** Every index is prefixed with `userId` because every query is scoped to the authenticated user — this keeps reads selective and supports the equality-then-range/sort pattern (e.g. equality on `userId`, range/sort on `dueDate`). The text index powers search; avoid over-indexing to keep writes cheap.

### 4.3 Validation rules

- `title` length 1–120; `description` length ≤ 2000.
- `status` ∈ `["TODO","IN_PROGRESS","DONE"]`; `priority` ∈ `["LOW","MEDIUM","HIGH"]`.
- `userId` required and set by the backend; clients can never set or change it.
- If `categoryId` is present, the backend verifies the category exists and shares the same `userId`.
- `completedAt` is managed by the service: set when transitioning to `DONE`, cleared on any transition away from `DONE`.

## 5. Derived & Computed Values

These are **not stored**; they are computed at read time:

| Value | Definition |
|-------|------------|
| `isOverdue` | `dueDate < now AND status != DONE`. |
| `completionRate` | `count(status=DONE) / count(all)` for the user, as a percentage. |
| Dashboard counts | Aggregations grouped by `status` and `priority` over the user's tasks. |

Computing these on read avoids stale denormalised counters and keeps writes simple. Dashboard aggregations use MongoDB's aggregation pipeline (`$match` on `userId`, then `$group`).

## 7. Collection-Level Schema Validation (MongoDB `$jsonSchema`)

Applied at the database level in addition to application validation, for defence in depth. Example for `tasks`:

```json
{
  "$jsonSchema": {
    "bsonType": "object",
    "required": ["userId", "title", "status", "priority", "createdAt", "updatedAt"],
    "properties": {
      "userId":      { "bsonType": "objectId" },
      "categoryId":  { "bsonType": ["objectId", "null"] },
      "title":       { "bsonType": "string", "minLength": 1, "maxLength": 120 },
      "description": { "bsonType": "string", "maxLength": 2000 },
      "status":      { "enum": ["TODO", "IN_PROGRESS", "DONE"] },
      "priority":    { "enum": ["LOW", "MEDIUM", "HIGH"] },
      "dueDate":     { "bsonType": ["date", "null"] },
      "completedAt": { "bsonType": ["date", "null"] },
      "tags":        { "bsonType": "array", "items": { "bsonType": "string" } },
      "position":    { "bsonType": ["int", "double", "null"] },
      "createdAt":   { "bsonType": "date" },
      "updatedAt":   { "bsonType": "date" }
    }
  }
}
```

## 8. Data Lifecycle & Integrity Notes

- **Cascade on account deletion.** Deleting a user removes their `tasks` and `categories` (handled transactionally at the service layer).
- **Category deletion.** Deleting a category sets `categoryId` to `null` on its tasks (tasks are not deleted) — work is never lost because a grouping was removed.
- **Timestamps.** `createdAt`/`updatedAt` are managed by Spring Data auditing (`@CreatedDate`, `@LastModifiedDate`).
- **No cross-user references.** A task's `categoryId` must resolve to a category with the same `userId`; enforced before write.
